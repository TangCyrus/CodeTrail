# 小范围试用验收与主持人评分标准

适用任务版本：trial-v1，CodeTrail 0.10.0。此文件包含参考答案，交卷前不展示。工程准入与用户效果是两个不同结论；工程通过才能邀请试用，不表示用户任务已经通过。

## 工程准入

- CodeTrail 自身和固定 TanStack Store 各完成 T1/T2/T3，共六个任务流程。入口、推荐、搜索、上下游、源码证据可达；不能只验证内部函数而绕过 MCP。
- 项目根目录、HEAD、版本与依赖环境已记录。自分析应无诊断；TanStack 允许既有 partial，但必须记录两侧诊断、正常外部引用、真实缺口和基线声明拒绝原因，不把 partial 变成 complete。
- T2 的语句通过实际源码核对；T3 的变化与旧新源码对应，两侧各有直接 CALLS 路径和同侧证据。概览、聚焦的截断及分页限制均保留。
- 恢复练习后旧报告过期，两侧练习源码仍可读取；新比较零变化、零影响路径。原始文件逐字节恢复，HEAD 不变，外部克隆干净。不覆盖并发编辑。
- 工具调用无未处理错误，单次结果不超过现有 48,000 字符预算；不增加时限或分析预算掩盖失败。实际等待单独记录，不用脚本速度替代真人理解耗时。

P0：串用旧新证据、错误指认源码/项目、丢失用户改动或给出虚假的完整性结论；发生即暂停邀请，修复并重跑两项目。P1：接入失败、目标无法定位、证据打不开或无法完成比较，且无可用的明确降级路径；核心链路需修复后再邀请。P2：可绕过的导航/文案问题、已声明的局部解析缺口；记录影响与绕行方式，可以进入试用。正常 external、明确 partial 或截断本身不自动计为产品故障。

## 任务评分（每项 0–4 分）

每满足一个检查点得 1 分，不以表达术语评分；0 分为没有有效完成。某项达到 3 分且必需点满足，才算正确性通过。状态另记 `independent`、`assisted`、`timeout`、`blocked` 或 `abandoned`，不能用分数隐藏帮助和未完成。

T1 四个检查点：三个合理模块/文件职责且能指出依据；至少一个进入位置并区分导出/启动与规则候选；一条有源码位置的调用关系（必需）；3–5 步有理由的阅读顺序并注明至少一个不确定边界。目录名不等于业务边界，推荐排名不等于业务重要性。

T2 四个检查点：准确定位目标语句和符号（必需）；解释修改边界且未把分页/其他同名逻辑当目标；至少一个有源码依据的调用者；提出可定位的测试检查与行为差异/边界。测试来自普通文件搜索也有效，但需注明来源。

T3 四个检查点：变化文件、符号和两侧语句正确；直接调用路径及两侧对应的证据身份正确（必需）；有依据的测试建议并明确未知/截断；恢复后验证原文保留与零改动。C 条件可使用主持人提供的只读旧新原文与 Git diff，不因缺少 CodeTrail 缓存而扣分；需要说明证据从何而来。若混用 side、使用过期结果描述当前状态或宣称静态路径证明执行/覆盖，则 T3 不能通过，记录为证据误判。

信心与正确性独立记录。高信心（4–5）且证据误判是优先调查问题。主持人不替参与者补全答案；遇到提示操作方式、提示位置或代操作，逐条保存，并由另一位核对者复核歧义评分。尚无第二核对者时标记未复核，不虚构一致率。

## 真人结果的扩大条件

首轮按原计划完成六人试用后，再决定是否扩大：没有未解决的 P0/P1；T 条件每个任务至少 5/6 人独立完成且正确性通过；证据误判逐个复核，T 条件正确性不得低于可比较的 C 条件。分母包含超时与阻断，缺席者不算完成；样本不足时只报告实际人数，不宣称达标。

这些是下一轮是否值得扩大的探索性门槛，不是统计显著性或正式发布承诺。耗时、帮助次数和主观反馈用于选择改进方向；不以更快但更错误为成功。真实模型语义质量和自主工具选择需另外核对聊天与发送范围，工程脚本通过不代替这部分验收。
